# August 11, 2026

## What We Built

- People can now create or access a SaaSassin Performance account with Google as well as email and password.
- The authentication card now carries the accepted SaaSassin mark and a distinct Performance lockup instead of a generic security icon.
- The Google action changes between “Sign up with Google” and “Sign in with Google” so the active account mode stays explicit.
- The full ten-product fleet now has a capability-named identity, canonical
  subdomain route, domain model, golden workflow, scope boundary, and vertical
  delivery contract.
- Builders can inspect every foundation from the new `/apps` fleet page; each app
  shell exposes its real object model, delivery sequence, and trust invariants.
- Ten self-contained Claude prompts now hand off the exact build scope, evidence
  gate, security requirements, verification, and deployment contract per app.
- Every fleet product is live on its capability subdomain with Vercel TLS, explicit
  GoDaddy CNAME records, Firebase Auth authorization, and canonical legacy redirects.

## What We Fixed

- Google is enabled as a production Firebase Authentication provider, with the canonical SaaSassin domains and localhost registered as authorized origins.
- Google popup, account-choice cancellation, popup blocking, conflicting account methods, and provider availability now produce clear states instead of raw Firebase errors.
- The auth hierarchy now presents the lowest-friction path first while retaining the complete email/password flow.

## Key Decisions

- SaaSassin Performance uses the accepted parent-brand mark rather than imitating Lattice’s protected identity.
- The Google button uses Google’s official color mark, white background, border, sizing, and action copy guidance.
- Both authentication methods terminate in the same server-created, HTTP-only Firebase session and tenant authorization path.
- Capability subdomains replace incumbent names in product URLs: Performance,
  Research, Planner, Creator, Feedback, Studies, Revenue, Community, Mail, and Trust.
- One Next.js/Vercel project hosts the incubation fleet until independent teams,
  runtime/compliance needs, or deploy cadence justify a split; stable host routing
  preserves product URLs through that future move.
- Product foundations are honest `noindex` build contracts, not fake finished
  dashboards. Performance remains active and Feedback remains upstream-blocked.
- Explicit CNAMEs were used instead of a wildcard so the publicly enabled fleet is
  auditable and unknown subdomains do not route into the application.
